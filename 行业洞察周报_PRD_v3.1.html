1. 背景与目标

1.1 背景

投研与金融科技从业者需要持续跟踪行业运行状况，但信息获取存在三个结构性痛点：

  • 信息过载与碎片化：关注领域每天产生大量资讯，散落在新闻客户端、公众号、研报平台、监管公告、海外媒体等多个渠道，人工跨平台搜集成本高。
  • 缺乏横截面视角：单点新闻只能回答"发生了什么"，无法回答"本周哪个赛道在发生密集变化"。
  • 缺乏量化回顾：看过的资讯无法沉淀为可比较的时序数据，景气度迁移、赛道冷热变化只能凭印象，无法回顾验证。

1.2 产品目标

编号 目标 衡量方式
G1 自动产出三域周度动态概览，替代人工跨平台搜集 人工搜集耗时从每周 4-6 小时降至 ≤30 分钟（仅复核）
G2 对 AI、人形机器人、脑机接口、半导体四个赛道提供高灵敏度追踪 四赛道重大事件 3 小时内进入页面
G3 建立横截面比较能力，快速定位本周"变化最密集"的赛道 60 秒内判断本周 Top 5 活跃赛道及驱动事件
G4 每条动态可回溯原文，杜绝无源结论 100% 条目携带 ≥1 条原始链接
G5 形成可检索的历史知识库 支持检索 52 周以上历史条目
G6 通过可视化图表呈现赛道景气迁移与结构变化（v3.0 新增） 可在 30 秒内从看板读出近 12 周赛道冷热变化

1.3 非目标（本期明确不做）

  • 不做行情与量化数据：不接入股价、K 线、财务数据、估值指标。本产品解决"事件与叙事"，不解决"定价"。
  • 不做投资建议输出：不生成买卖信号、不做标的推荐。
  • 不做金融机构日常经营跟踪（v3.0 新增边界）：银行的存贷数据、保险保费、券商经纪业务等金融机构经营动态不属于收录范围，除非该事件直接指向"资金流向变化"或"对某赛道的投资观点"。此边界用于避免投资域又退回成金融行业域。
  • 不做多用户协作与权限体系。
  • 不做移动端原生 App：仅保证移动端浏览器可用。
  • 不做邮件/消息推送。

1.4 使用场景

场景 描述 频次
S1 周度扫读 每周固定时间（周一晨间）打开首页，10 分钟内扫完三域本周要点 每周 1 次
S2 核心赛道深挖 对四个核心赛道随时查看最新进展与事件脉络 每日/每周数次
S3 看板回顾（新增） 打开数据看板，看近 12 周赛道景气迁移、市场结构变化 每周/每月 1 次
S4 回溯检索 面试/写作/研究时检索"某赛道某时间段发生了什么" 按需
S5 临时补充与修正 补录管线漏掉的信息，或修正错误归类 每周 1-2 次

2. 分类体系

采用 三维分类：域 × 赛道 定内容归属，市场 定主体地域，内容类型 定事实/观点。

2.2 核心关注机制

TEC-AI / TEC-ROBO / TEC-BCI / TEC-SEMI 标记 focus: true：

  1. 首页置顶：大卡片置于页面最上方。
  2. 采集加权：采集频率每 3 小时（其他每 6 小时）。
  3. 重要度加成：× 1.15（上限 100）。
  4. 看板突出（v3.0 新增）：数据看板中核心赛道使用主色 #1B3A5C，其余使用灰蓝。
  5. 固定不变（v3.1 确认）：核心关注赛道固定为上述四个，不提供产品化的动态调整入口；确需变更时直接修改 config/taxonomy.yml 中的 is_focus 字段。

5. 处理管线（Pipeline）

# 阶段 关键规则
P1 采集 见 §4.3
P2 清洗 提取标题/正文/时间/作者/URL；剔除 <200 字、广告、荐股内容
P3 去重 三级去重，生成归并组
P4 分类 Gemini 判定 域×赛道 + 市场 + 内容类型；置信度 <0.6 进入待人工归类队列
P5 打分 见 §5.1；核心赛道 ×1.15；<40 进入低优先级池
P6 摘要 Gemini 生成 1-2 句客观摘要；禁止推断、禁止补写原文没有的数字
P7 校验 校验原文链接可访问 + 摘要实体可在原文定位；失败回退重试一次，仍失败丢弃
P8 统计 v3.0 新增：由代码（非 LLM）计算看板所需的全部统计指标，输出 data/stats/*.json
P9 构建发布 应用 overrides → 生成静态页面与图表 → 提交 → 部署

5.1 重要度评分模型（满分 100 · 仅事实类）

维度 权重 说明
信源等级 25 S/A/B/C/D/E → 25/20/17/15/12/8
事件类型 25 政策出台/重大并购/业绩暴雷/技术突破 = 25；常规经营 = 10
影响广度 20 影响全赛道 = 20；单一公司 = 5
报道密度 20 N 个独立信源报道，上限 20
时效性 10 24h = 10；7 天内 = 5；更早 = 2

分级：≥75 关键信号｜60-74 重要｜40-59 一般｜<40 低优先级

核心关注加成 ×1.15（上限 100）；观点类不参与本模型。

5.2 活跃度口径

赛道周活跃度 = Σ(事实类条目重要度分) × 0.6 + 事实类条目数 × 10 × 0.4
趋势判定：与上周比较，变动 >±15% 记为 up/down，否则 flat

口径固化并展示在看板页脚。

5.3 反幻觉约束（硬性）

  1. 每条发布态条目必须携带 ≥1 条可访问原文 URL，无源不发布。
  2. 摘要中所有数字、主体、时间必须可在原文定位；P7 实体级校验。
  3. 分类置信度不足进入人工队列，不得猜测归类。
  4. AI 生成内容显式标注生成标识与时间，摘要与原文可一键对照。
  5. 看板的统计结论由代码计算，不由 LLM 生成（v3.0 新增）——避免统计类数字出现幻觉。

6. 部署架构

6.1 方案（已确定）：公开仓库 + GitHub Pages + Actions

项 选择
仓库可见性 Public（Free 账户的 Pages 仅对公开仓库开放）
静态托管 GitHub Pages（仓库 gh-pages 分支或 /docs）
定时管线 GitHub Actions（公开仓库免费额度不限）
成本 0 元（托管）+ LLM 费用

已知代价：站点内容任何人可访问。缓解判断——内容全部是公开新闻的 AI 摘要 + 原文链接，不含持仓、不含个人笔记，实际暴露面很小。若后续在意，可迁移至「私有仓库 + Cloudflare Pages + Access」，静态站迁移成本低。

6.2 LLM：Google Gemini

项 配置
供应商 Google Gemini API
密钥管理 存于仓库 Settings → Secrets（GEMINI_API_KEY），绝不入库，工作流中以环境变量注入
型号策略 高频轻量任务（分类、摘要）用轻量型号；复杂归类与低置信度复核用能力更强的型号。具体型号在 config 中指定，按启用时官方可用列表确定
成本上限 月度预算上限（建议 ≤￥100），超限自动降级为"仅采集不摘要"
网络可达性 Gemini API 在中国大陆网络环境通常不可直接访问，但 GitHub Actions 运行于境外，天然可达，无需代理

待办（启用前确认）：Gemini API 免费层的数据使用条款（是否用于模型改进）与速率限制，需在使用前确认当期政策；若条款不接受，改用付费层。

6.4 修正层：文件级替代后台 UI

GitHub Pages 为纯静态托管，无服务端与数据库，传统登录后台不成立。单人使用场景下改为编辑配置文件 + 提交触发重建。

data/overrides.yml 支持五种操作：

  id: evt_2026W44_0201

  content_type: fact

- op: rescore
  id: evt_2026W44_0088
  score: 82

- op: delete
  id: evt_2026W44_0455
  reason: 荐股内容

- op: add
  week: 2026-W44

  track: TEC-BCI

6.5 更新节奏

项 规则
采集 核心赛道每 3 小时；其余每 6 小时
页面重建 采集产生新条目后自动触发；无变化不触发
数据延迟 核心赛道 ≤3 小时，其余 ≤6 小时
周报快照 每周一 07:00（Asia/Shanghai）冻结上一周数据
实时流 首页实时流始终展示本周至今全部条目

GitHub Actions cron 不保证精确触发，高峰期可能延迟数分钟至数十分钟，周报场景可接受。采集任务每次 commit 数据，天然维持仓库活跃，避免 scheduled workflow 因长期无活动被禁用。

7. 数据可视化看板（v3.0 新增）

7.1 设计原则

原则 说明
口径优先 每张图下方标注计算口径，避免误读
统计不幻觉 所有指标由代码在构建期计算，不使用 LLM 生成数字
无外部依赖 图表以自绘 SVG 输出，不引入 ECharts/D3 等外部库，保证加载快、体积小（仓库 1GB 上限）、风格统一
可下钻 点击图表中任一赛道跳转至该赛道详情页
核心突出 四个核心关注赛道用主色 #1B3A5C，其余用灰蓝

技术选型判断：本项目图表类型仅为条形图、折线图、热力矩阵、堆叠条四类，自绘 SVG 完全覆盖，且省去约 1MB 的库体积与 CDN 依赖。若后续需要缩放、联动等复杂交互，再引入轻量图表库，届时只需替换渲染层。
